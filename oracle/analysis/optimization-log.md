# Optimization log

Every entry: hypothesis → change → expected reason → correctness → before/after → plan change → decision.
Timings are medians of hot, prepared executions on Oracle AI Database 26ai Free 23.26.4 (arm64,
`cpu_count=2`), unless stated otherwise. Correctness is against the CedarDB reference frames
(`tests/run_correctness.py`).

## 0. Calibration micro-benchmarks (before any renderer)

Purpose: learn what a pixel *costs* in Oracle so the design is driven by measurement. Synthetic
workload: 320 column spans × 168 rows = 53,760 pixel rows (one 3-D view), generated by a range
join of a 320-row span table with a 200-row `screen_y` IOT (`y BETWEEN y0 AND y1`).
Scripts: `benchmark/calibration/`.

| Operation over 53,760 pixel rows | ms | Δ vs join only |
|---|---|---|
| range join, `COUNT(*)` | 3.4 | — |
| + `SUM(y)` with second join to a 320-row `screen_x` | 8.8 | |
| + `MOD(FLOOR(v0+(y−y0)·step),128)` texel-row arithmetic (5 ops) | 18.5 | +15 (≈0.056 µs/op/px) |
| NUMBER vs BINARY_DOUBLE for that arithmetic | 18.5 vs 19.1 | no difference |
| + `SUBSTR` of a 256-char hex `VARCHAR2` (AL32UTF8) | 53.3 | char semantics scan the string: O(n) per call |
| + `SUBSTRB` (byte semantics) of the same string | 26.0 | O(1) |
| + `UTL_RAW.SUBSTR` of a `RAW` | 133.7 | PL/SQL package call per pixel — rejected |
| texel IOT lookup `JOIN texel ON (tid, v)` (NL or hash) | 29 | ≈ +10 |
| `TO_NUMBER(SUBSTRB(dec3,…))` numeric texel | 34 | `TO_NUMBER` ≈ +15 |
| `TO_NUMBER(hex,'XX')` | 537 | rejected |
| **`ASCII(SUBSTR(nvarchar2, c0 + y·step, 1))`** | **24.4** | AL16UTF16 is fixed-width: O(1); `SUBSTR` truncates the fractional position = free `FLOOR`; `ASCII()` returns the UTF-16 code unit exactly (U+0100+i ↦ 256+i) |
| `TRANSLATE` of 320 × 512-char columns (per column, not per pixel) | 142 | ≈0.9 µs/char — colormap-by-TRANSLATE rejected |

Framebuffer assembly from 53,760 pixel rows:

| Assembly | ms | notes |
|---|---|---|
| `LISTAGG(..) WITHIN GROUP (ORDER BY x) GROUP BY y` | +20 | the sort is the cost |
| `LISTAGG` without `WITHIN GROUP` | +2 | **order not preserved** — verified wrong, rejected |
| `XMLAGG` | +250 | rejected |
| **`SUM(idx · 256^(x mod 15)) GROUP BY y, x div 15`** | **+5** | order-free, hash group by; 15 pixels per exact 38-digit `NUMBER`; client decodes base-256 digits |

Generic per-pixel depth resolve (80,640 fragments → 53,760 pixels):

| Resolve | ms |
|---|---|
| `MIN(packed key) GROUP BY pix` | 40.0 |
| `MIN(k) KEEP (DENSE_RANK FIRST ORDER BY k) GROUP BY pix` | 46.5 |
| `ROW_NUMBER() OVER (PARTITION BY pix ORDER BY k) = 1` | 71.7 |

**Conclusions that shape the design**
1. Row *generation* is cheap; per-pixel *expressions* and *sorts* are what cost. Budget ≈0.06 µs
   per operator per pixel; a 35 FPS frame (28.6 ms) affords only ~5–8 operators per pixel in total.
2. A generic z-buffer alone (~35 ms) exceeds the frame budget in Oracle. Visibility must be
   resolved structurally at interval level so each pixel row is generated exactly once.
3. Texels: `NVARCHAR2` columns of single-code-unit characters, `ASCII(SUBSTR(...))`.
4. Framebuffer: order-free `SUM` packing instead of `LISTAGG ... ORDER BY`.
5. `KEEP (DENSE_RANK FIRST)` is slower than a packed-key `MIN` for winner selection here (H19).

## Tuning round 1

Primary metric: `tests/quicktime.py` (hot median exec/total over tics 100..1100). Per-tic A/B:
new `tests/tictime.py a.sql,b.sql` (interleaved, cancels drift); stage A/B: new `tests/abtest.py`
(textual variants of the built SQL, `COUNT(*)`/custom tail/`FULL`); real-plan sampling: new
`tests/ash_profile.py` (V$ACTIVE_SESSION_HISTORY by plan line); `tests/planbasic.py`
(uninstrumented plan of any tail); `tests/plan_full.py` (instrumented, lines above an A-Time).
Saved parts per step: `sql/variants/r0` (start) … `r6_pre_keep` (= final);
`sql/variants/build_variant.py <dir>` builds `sql/variants/<dir>.sql` for side-by-side timing.

Start: quicktime exec 243.2 / total 251.1 ms; per tic 100:288 300:160 500:334 700:234 900:251 1100:86.

**C1. Correctness fix: CedarDB pose conversion (not a performance experiment).** The CedarDB
ground truth got the pose as SQL literals (Python repr) converted as float8(mantissa)/10^scale,
sometimes 1 ulp off. Ported `pose_conv` from render_baseline.sql. The literal port cost **59 ms**
per frame (`cam` alone; NUMBER `LOG`/`POWER` in a lateral over `nums` re-evaluated per row) and its
changed estimates made `items` blow PGA_AGGREGATE_LIMIT (ORA-04036). Rewritten: python-oracledb
binds a float as NUMBER whose digits ARE Python's repr (checked with `DUMP(:px)`), so scale =
decimal places of `TO_CHAR(:px,'TM9')`, mantissa = :px·10^scale, rounded to 53 bits (ties even) in
exact NUMBER, then `TO_BINARY_DOUBLE(m)/TO_BINARY_DOUBLE(10^scale)`. Bit-identical to the baseline
`pose_conv` on all 4,800 pose values (211 differ from the raw bind); 0.3 ms. Also skycol's
`256d/90d` → `2.844444d` (CedarDB numeric 256.0/90.0, as in the baseline; the doubles differ).
Correctness step 25: 48/48 exact. Kept.

**E1. pspx: drop the screen_x probe per weapon texel column.** Hypothesis from the instrumented
FULL plan at tic 500: `INDEX RANGE SCAN SCREEN_X_PK` with 3,310 starts took 130 ms (the
`x BETWEEN f(l.xl)` + `sc.u = x.x - FLOOR(l.xl)` probe walks the index range per row). Change:
x = xl0 + sc.u with sc.u range-bounded, then (after the first try still produced a 112k-row
cmap×sprite_col hash join, E-Rows=1) weapon layers precomputed in a new materialized 1–2-row
CTE `wlay` (integer origin + light), pspx = `LEADING(l sc y) USE_NL`, ov weapon branch
`LEADING(p cm) USE_HASH(cm)`. tic 500 FULL 358 → 229; quicktime per-tic mean 225.5 → 140.3
(median 242 → 140). Step 50 exact. **Kept — the round's big win (≈ −100 ms/frame, every frame has a
weapon).**

**E2. skycol: per-column u first, then indexed texcol_lit probe** (`NO_MERGE` inline view +
`USE_NL INDEX(t texcol_lit_pk)`, materialized). Standalone stage plan showed an INDEX FAST FULL SCAN
of TEXCOL_LIT_PK (24.7k buffers) hashed to 320 columns: bg_sky stage 185 → 94 ms. In FULL the plan
was already different, so the end-to-end gain is ~1 ms (tictime mean 140.3 → 139.7). Kept for
plan stability (removes a 735k-row-index scan from the plan space).

**E3. MATERIALIZE wparts.** Plan of pcols showed the wall-part unpivot (`wall_part_kind` CASE join)
evaluated AFTER the screen_x expansion (per (seg, column, kind)): the `LEADING(w x mo)` hint in
wcol was lost because wparts was merged. pcols stage 45 → 22 ms; FULL unchanged-to −1 ms
(the FULL plan had already a better order). Kept (stability; costs < 0.3 ms).

**E4. flused driven from DISTINCT visible flats** (`USE_NL INDEX(fl flat_lit_pk)` instead of a
hash semi-join over an INDEX FAST FULL SCAN of all 13,464 lit flat strings, 4.5k buffers; ASH put
8% of samples on that line). −0.5…−1 ms (tictime 138.3 → 137.7). Kept.

**E5 (failed). Window-function cost in pclip.** Measured by ablation at tic 500: no windows
23.8 ms, one window 31, all six 41 (the first window's sort ≈7 ms, each further window ≈2 ms on
6.5k rows). Variants: frames ending at CURRENT ROW instead of 1 PRECEDING (−2 ms, would change
results), without LAST_VALUE IGNORE NULLS (−3 ms), without the two partition-only MINs (−1 ms).
Nothing worth a rewrite. Not changed.

**E6 (failed). Packed MIN instead of KEEP (DENSE_RANK FIRST) in segcls/contested.** Exact packing
needs NUMBER (`TO_NUMBER(key/16384d)*1e6 + item_id`; key/16384 is an exact integer < 2^53): tictime
mean 136.0 → 148.2 (TO_NUMBER per candidate row costs more than KEEP). A BINARY_DOUBLE packing
looked 15 ms faster in an A/B but is inexact (keys up to 2^67) → wrong winners, less pixel work:
an artefact. Reverted.

**E7 (failed). NUMBER decode of cc_pack/cf_pack in pspan_raw** suspected (7 NUMBER ops/row/branch):
ablating it changed nothing (208.8 vs 209.4 ms). Not changed.

**E8 (failed). Statement-level OPT_PARAMs** `_rowsets_enabled=false`, `_rowsets_max_rows=1024`,
`_optimizer_vector_transformation=false`: all within ±1 ms. Not changed.

**E9 (failed). Single BINARY_DOUBLE hash key for the per-pixel flat join**
(flat_id·256 + light·4 + quarter instead of three keys incl. a NUMBER flat_id): 136.0 → 138.1.
Reverted (saved as sql/variants/r7_flatkey_rejected_opt_pixels.sql).

**Ablations at tic 500 (FULL ≈ 210 ms hot) — where the time is now:** front end through fseg
≈ 88 ms (2 ms of it is round trip/exec overhead; pclip +24, items +16, segcls +11 for 2–10k-row
stages ≈ 1–3 µs/row/stage); background pixels ≈ 70 ms (54k-row generation by NL range scan only
≈ 6 ms; flats ≈ 1.7 µs/px — depth, world x/y, zlight, 3-key hash probe, SUBSTR; walls ≈ 1.5 µs/px);
sprites ≈ 12 ms; status bar ≈ 4 ms; overlay join + packing SUM ≈ 10 ms.

End: quicktime exec 135.3 / total 143.3 ms (−44%); per tic 100:134 300:132 500:198 700:164 900:139
1100:51. Hot cumulative profile at tic 300 (ms, before → after): bsp 6.5 → 6.6, segh 11.4 → 11.7,
wvert 21.7 → 18.1, pclip 38.5 → 30.1, fseg 56.7 → 56.3, bg 83.5 → 85.7, packed 130.8 → 107.6,
FULL 166.1 → 144.1. Correctness: step 10, 120/120 frames exact.

**Conclusion.** No remaining SQL-level option closes the gap to ~33 ms. The single-statement
relational renderer bottoms out at ≈ 60–100 ms/frame on this 2-CPU instance (≈ 1–3 µs per row
per front-end stage, ≈ 1.5 µs per pixel). Next: the hybrid architecture (geometry/visibility in
SQL, per-pixel inner loops in natively compiled PL/SQL), measured against the pure-SQL renderer
as the brief requires (H27).

## Hybrid renderer (H27)

`sql/render_hybrid.sql` (one prepared SELECT, same binds, `hexrows` output) over the pipelined
function `doom_hybrid.render_frame` (`sql/06_hybrid.sql`, installed by `client/install_hybrid.py`,
last step of `client/setup_db.py`). Design summary: `hybrid-design.md`. Source snapshots of every
step: `sql/variants/h1_06_hybrid.sql` … `h10_06_hybrid_final.sql`.

**Architecture boundary.**
* SQL (per frame, BULK COLLECT / SELECT INTO, 4 statements): player/weapon/HUD state incl. the
  palette number and an owned-weapons bitmask (1 row); sectors with the animated-light thinker
  formulas (`alight`, NUMBER `MOD` arithmetic kept verbatim); per-tic seg texture overrides; the
  sprite list (`thing_view` verbatim: joins of 12 state/catalog tables, depth/side, `ATAN2`
  rotation). These are state retrieval over the `st_*` tables, where SQL is the natural tool.
* PL/SQL: everything camera-dependent and per pixel: CedarDB pose conversion (NUMBER math, same
  as `pose_conv`), BSP frustum keep + front side + order-statistic rank, back-face cull,
  transform, near clip, projection, the 7-way wall-part unpivot, solid occlusion, wall columns,
  per-column visplane clip windows (sort by (depth_x, bsp_seq, part, seg_id), running MAX/MIN,
  carried planes), plane spans incl. seeds, an exact per-pixel z-buffer on the reference key,
  texturing/lighting/COLORMAP of winners, sprite frame choice and bounds (float4 tops), weapon
  psprite, pickup message, status bar, hex rows.
* Static package caches (immutable WAD data, loaded on the first call per map; nothing camera-,
  tic- or frame-specific): BSP nodes/children/steps, render_segs_ext with resolved texture codes,
  texel arrays (walls column-major, flats, sprite pixels with mask; lazily per texture, ~0.93 M
  texels after the whole run), COLORMAP, sprite_frames, ui patches, status-bar background,
  mod-64/light-clamp/hex lookup tables. Session PGA with all caches warm: 84 MB. Cold first frame
  222 ms.

**Exactness.** The z-buffer key is the reference's 64-bit key: `ROUND(clamp(depth,0,131071)*4096)·2^20
+ ((2−surface)·4+src)·2^16 + stable` is < 2^49, so it is exact in one BINARY_DOUBLE; the light/palette
low bits are compared only on a tie of that key (computed then for both fragments). Checked: PL/SQL
`COS/SIN/TAN/ATAN/ATAN2` = SQL on 100k inputs; PL/SQL `ROUND(BINARY_DOUBLE)` rounds half-even like
SQL; PL/SQL BINARY_FLOAT `base_z + top_offset` and `− height` = SQL on all 814,592 (base_z,
top_offset, height) combinations of the run (`tests/hybrid_float4_check.py`); `LEAST/GREATEST`
NULL semantics written out as branches; sky constant 2.844444; masked midtextures opaque; plane
depth cap; seeds. Correctness: **1200/1200 tics pixel-exact** (step 1), step 5 240/240, step 25 48/48,
palette numbers all correct. No frame class needed special handling.

**Native vs interpreted.** `ALTER SESSION SET plsql_code_type = NATIVE` compiles the units VALID but
records `PLS-00924: native compilation is not supported on this platform` (Oracle AI Database 26ai
Free 23.26.4, linux/arm64); `USER_PLSQL_OBJECT_SETTINGS` still says NATIVE. Measured on the final
code: NATIVE build 26.3 ms, INTERPRETED build 26.8 ms (quicktime total, 3 runs each) — the same
M-code interpreter, difference is noise. Calibration of the interpreter (micro-benchmarks, ns per
operation, hot): simple statement/loop step 15–20; array read 5–10, write 12–15; BINARY_DOUBLE
op ≈5, `FLOOR` ≈0; BINARY_DOUBLE→PLS_INTEGER conversion 30–50; integer `MOD`/division 80–90;
procedure/function call 0.5–1 µs (profiler); lookup in a ~1M-entry array with texture-like
locality ≈17 (≈100 with random access). Package-level vs local collections: no difference.
`PLSQL_OPTIMIZE_LEVEL=3`: 28.1 vs 29.0 ms at level 2 (kept 3).

## Hybrid round 2

Goal: every frame ≤ 33 ms, pixel-exact, interpreted PL/SQL (native compilation unavailable:
PLS-00924 on linux/arm64). Start: `final_hybrid` = mean 26.2, p50 27.2, p95 34.6, p99 36.7,
max 44.1 ms, 38.2 FPS, 90.3% of frames ≤ 33 ms (105 frames above, almost all in tics 450–590).
Snapshots: `sql/variants/h11_…` … `h22_06_hybrid_final.sql` (rejected ones are marked
`_rejected`). Measurements: `tests/hybrid_phases.py` (hot per-phase medians), `tests/quicktime.py`,
full runs with `benchmark/bench.py` (labels `r2_h12`, `r2_h16`, `r2_h20`, `final_hybrid_r2`).
Exactness gate after every kept change: `run_correctness --step 25` 48/48; denser checks noted.

**What the interpreter charges (micro-benchmarks, 53,760 iterations, hot).** Full-screen wall loop
as in h10 9.2 ms (≈170 ns/px); the same with the z-test streamlined (one `zq` read, no owner
write, no tie branch) 7.3; without any z-test 6.4–7.2; a plain constant write 1.15 (loop + write
≈ 21 ns). A streamlined z-test therefore costs ≈ 18 ns per winning pixel and ≈ 20–30 ns per losing
fragment. Flat texel: ≈ 165 ns/px even without z, dominated by five array lookups (≈ 20 ns each,
incl. the double→integer subscript conversions); `SIMPLE_DOUBLE`/`SIMPLE_INTEGER` locals: no gain
(8.99 vs 8.66 ms); nested tables / VARRAYs instead of `INDEX BY` arrays: copy 0.19 vs 0.23 ms,
element access 5–15% slower (rejected); strided reads 1.7× sequential ones.

**Fragment census (instrumented build, h10).** Tic 500: 36.3k wall fragments (26.4k wins),
53.2k plane fragments (28.0k wins); tic 897: all 19.1k plane fragments lose; wall-vs-wall key
ties: 0 in every frame (by construction, below); plane-vs-plane ties 0–300 per frame. After
h11–h19: plane losers at tic 500 were 24.2k against other planes, 60 against walls, and 24.0k of
them sat in 633 spans that won no pixel at all → h20.

**Experiment 1, full structural ownership (not built; bounded by measurement).** The brief's
premise was that the per-pixel depth buffer is the cost of the two biggest phases. After h11 it is
not: a streamlined z-test is ≈ 18 ns per winning pixel (≈ 1 ms for a full screen) and ≈ 25 ns per
losing fragment, while texturing/lighting a pixel costs 100–200 ns and is needed by any exact
renderer. Eager shading already shades almost only winners (overdraw < 6%). A per-column
interval resolver (elementary segments, constant-key walls, plane-vs-wall crossing) costs
interpreter statements per item and per segment (≈ 10–30 statements × 15–20 ns for 5–16 items per
column) — of the same order as the z-test work it removes, with the sprite pass still needing a
per-pixel owner key. The parts of it that pay were implemented exactly: no owner/tie bookkeeping
outside sprites (h11), interval-level rejection of provably losing span parts (h19 bands, h20 seed
overlap — the latter removed 85–90% of all losing plane fragments).

**Experiment 2, floors/ceilings as horizontal runs (rejected by measurement).** With depth,
zlight and the depth-only plane terms constant per row, a row loop needs 6 lookups per pixel
instead of 11, but the buffers are column-major and stride-168 access is 1.7× slower: the same
53,760 flat pixels cost 11.4–12.2 ms vertical (streamlined) vs 10.0–10.9 ms horizontal (−12%,
before any span conversion), and 8.6–9.4 ms horizontal without z. Converting the per-column spans
into per-row runs (Doom's R_MakeSpans needs per-visplane top/bottom arrays, i.e. grouping spans by
plane key per column) would cost a large part of that ≤ 0.6 ms (heavy frames) gain. Texel reuse
along rows only hits when depth < 160 (step < 1 texel) and measured a loss even vertically, where
the check is cheapest. Row-constant hoisting that is free — per-height row tables — was already in
place; a per-(height, light) table (h15) did not pay either.

**What a collection element costs (package-level collections, V$MYSTAT deltas between calls).**
INDEX BY PLS_INTEGER / BINARY_DOUBLE / BINARY_FLOAT and nested tables: **≈ 30 B per element**

INDEX BY ≈ 5–10 ns, `ASCII(SUBSTRB(s, i, 1))` on a byte string ≈ 200 ns, unpacking 3 texels per
integer ≈ 190 ns — a denser texel representation costs ≈ +10 ms per frame (≈ 55k texel reads),
so the texel store stays one INDEX BY array of PLS_INTEGER.

**Decision / what remains.** With one render session the frame is still the period: the
single-session renderer is now within a few percent of what interpreted PL/SQL can do per pixel
(flats need two exact `FLOOR`s and ~11 lookups per pixel, walls one `FLOOR` and ~5), so serial

native PL/SQL on a platform that supports it.
